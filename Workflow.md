# Как работать над проектом

## Запуск проекта

### MongoDB в Docker

Запустите Docker Desktop, затем поднимите базу:

```bash
npm run db:up
```

`docker-compose.yml` запускает MongoDB 7.0 и ожидает успешного healthcheck.
База доступна только локально, по адресу `127.0.0.1:27017`, без аутентификации.
Данные сохраняются в именованном Docker-томе `mongodb-data`.
Обычная остановка сохраняет данные:

```bash
npm run db:down
```

В этой конфигурации клиент для просмотра БД не устанавливается.
Проверить состояние и содержимое можно встроенным в контейнер `mongosh`:

```bash
docker compose ps
docker compose exec mongodb mongosh six_cities --quiet --eval "db.offers.countDocuments()"
docker compose exec mongodb mongosh six_cities --quiet --eval "db.users.find({}, {password: 0}).toArray()"
```

### REST-приложение

Установите зависимости (`npm install`), скопируйте `.env.example` в `.env`
в корне проекта и задайте свои значения. В PowerShell:

```powershell
Copy-Item .env.example .env
```

Пример содержит демонстрационную соль. Замените её случайной строкой;
получить такую строку можно командой:

```bash
node --input-type=module -e "import {randomBytes} from 'node:crypto'; console.log(randomBytes(32).toString('hex'))"
```

Запуск с JSON-логами Pino:

```bash
npm start
```

Запуск с форматированием логов через pino-pretty:

```bash
npm run start:pretty
```

Оба сценария собирают TypeScript и запускают `dist/main.rest.js`. Пока приложение
проверяет настройки, выводит сообщение об инициализации с номером порта и завершается.
HTTP-сервер будет добавлен в следующих заданиях. Подключение к MongoDB сейчас
выполняет команда CLI `--import`; её модели и сервисы доступны и в REST-контейнере.
Обычный запуск пишет структурированные JSON-логи в stdout. В `start:pretty`
подключается транспорт pino-pretty; ошибка приложения сохраняет код завершения 1.
Ошибки конфигурации также выводятся через логер. Соль и адрес БД в обычный лог
не выводятся, их значения скрыты и в ошибках проверки схемы.

### CLI

Установите зависимости (`npm install`), затем запустите CLI:

```bash
npm run cli
npm run cli -- --help
npm run cli -- --version
npm run cli -- --import ./mocks/test-data.tsv mongodb://127.0.0.1:27017/six_cities
```

Сценарий `cli` собирает TypeScript и запускает `dist/main.cli.js`. Без аргументов
показывается справка. Для CLI используется `npm run cli`; `npm start` запускает
REST-приложение.
После сборки можно запускать `node dist/main.cli.js --import ./mocks/test-data.tsv mongodb://127.0.0.1:27017/six_cities`.
Ошибки выводятся в stderr, код завершения — 1; успешное выполнение — 0.
За один запуск выполняется одна команда.

Команда `--import <filepath.tsv> <mongodb-uri>` принимает путь к TSV и полную
строку подключения MongoDB, включая имя базы. Поддерживаются `mongodb://`
и `mongodb+srv://`. Для сервера с аутентификацией можно передать URI вида
`mongodb://<user>:<password>@<host>:<port>/<database>?authSource=admin`;
специальные символы логина/пароля необходимо кодировать для URL.

Импорт читает файл потоком и сохраняет записи последовательно, без накопления
всего файла в памяти. Автор ищется по email и создаётся, если ещё отсутствует.
Каждое предложение сохраняется с `authorId`, ссылающимся на пользователя.
Вместо содержимого предложений выводятся логи подключения, итоговое количество
сохранённых предложений и закрытие соединения. URI с паролем не логируется.
При ошибке файла или записи импорт останавливается; сообщение содержит файл,
номер строки и число уже сохранённых предложений. Соединение закрывается в `finally`.
Успешные записи не откатываются. Повторный запуск добавит предложения заново,
но повторно использует пользователей с тем же email.

Для генерации сначала запустите тестовый REST API в отдельном терминале:

```bash
npm run mock:server
```

Затем получите заготовки с ресурса `/offers`, создайте TSV и импортируйте его:

```bash
npm run cli -- --generate 100 ./mocks/generated.tsv http://localhost:3000/offers
npm run cli -- --import ./mocks/generated.tsv mongodb://127.0.0.1:27017/six_cities
```

`--generate <n> <filepath> <url>` принимает положительное целое безопасное число,
путь к TSV и полный HTTP(S) URL ресурса с массивом заготовок. Адрес сервера
передаётся аргументом, а не зашит в код. В `mocks/mock-server-data.json` подготовлено
шесть заготовок: названия, описания, города, превью, по шесть фотографий и авторы.
Ссылки на изображения используют демонстрационный домен example.com.
Команда проверяет ответ сервера и случайно выбирает заготовки, тип жилья,
дату за последние 30 дней, рейтинг, комнаты, гостей, стоимость, удобства и координаты
рядом с центром города. Избранное выключено, комментариев нет.
Запись выполняется потоком с учётом скорости диска; файл перезаписывается.
При ошибке записи может остаться неполный файл. Тайм-аут HTTP-запроса — 10 секунд.

Для проверки большого файла после сборки (понадобится несколько GB свободного места):

```bash
node --max-old-space-size=64 dist/main.cli.js --generate 4000000 ./mocks/large.tsv http://localhost:3000/offers
node --max-old-space-size=64 dist/main.cli.js --import ./mocks/large.tsv mongodb://127.0.0.1:27017/six_cities
```

Проверьте размер созданного файла: он должен превышать 2 GB. Импорт записывает
каждое предложение в MongoDB, поэтому время выполнения и размер базы зависят
от числа строк. После проверки удалите временный TSV.

На предыдущем этапе CLI, до добавления MongoDB, на Node.js 24.13.0 было сгенерировано и прочитано
3 637 414 предложений, размер TSV — 2 222 104 398 байт (больше 2 GiB).
Обе команды запущены с `--max-old-space-size=64` и завершились с кодом 0.
Генерация заняла около 132 секунд, импорт — 91 секунду. При импорте stdout
направлен в нулевое устройство; временный TSV после проверки удалён.

### Формат TSV

Файл в UTF-8, поля разделены табуляцией, одна строка — одно предложение.
Порядок 21 поля соответствует заголовку `mocks/test-data.tsv`:
`Title`, `Description`, `PublicationDate`, `City`, `PreviewImage`, `Images`,
`IsPremium`, `IsFavorite`, `Rating`, `Type`, `Rooms`, `Guests`, `Price`, `Goods`,
`AuthorName`, `AuthorEmail`, `AuthorAvatar`, `AuthorType`, `CommentsCount`,
`Latitude`, `Longitude`.

Заголовок необязателен. Списки изображений и удобств разделены `;`, флаги имеют
значения `true`/`false`, дробные числа используют точку. Пустые строки пропускаются,
поддерживаются LF, CRLF и UTF-8 BOM. Табуляции и переводы строк внутри полей
не допускаются. В тестовом файле `CommentsCount` равен 0: комментарии не импортируются.
Географические координаты города берутся из ТЗ, а последние два поля задают
координаты жилья. Автор сохраняется в коллекции `users`, а предложение —
в `offers` со ссылкой `authorId`. Комментарии не импортируются, их счётчик устанавливается в 0.
В существующем формате TSV пароля нет: для нового автора генерируется случайный
пароль длиной 12 символов; он не выводится в логи. Сервис пользователей хранит
только scrypt-хеш с индивидуальной случайной солью. Для последующего входа
такому пользователю потребуется механизм установки/сброса пароля.
Email нормализуется в нижний регистр и защищён уникальным индексом.
Если аватар отсутствует, сохраняется `avatar.svg`.
Обе коллекции содержат автоматически обновляемые `createdAt` и `updatedAt`.

### Переменные окружения

Для REST-приложения обязательны все три переменные:

- `PORT=3000` — целочисленный порт от 1 до 65535.
- `DB_HOST=127.0.0.1` — IP-адрес сервера MongoDB (IPv4 или IPv6).
  Имя хоста вроде `localhost` и строка подключения MongoDB здесь не допускаются.
- `SALT=example-only-change-this-random-salt-7f8c2a` — непустая соль для будущего
  хеширования паролей; задайте собственную случайную строку.

`dotenv` читает `.env` из текущей рабочей директории, затем `convict` приводит
значения к нужным типам и проверяет схему. Запускайте приложение из корня проекта.
Уже установленные переменные окружения имеют приоритет над `.env`.
Значений по умолчанию в схеме нет: пропущенные, пустые и некорректные значения
прерывают запуск с кодом 1. Если все переменные заданы извне, `.env` необязателен.
Настоящие `.env` и `.env.*` исключены из Git; `.env.example` можно коммитить.

Для текущего CLI переменные окружения не требуются. Путь к TSV задаётся аргументом
`--import`/`--generate`, URL сервера — аргументом `--generate`, полная строка
подключения к MongoDB — вторым аргументом `--import`. Настройки REST-конфигурации
для CLI не требуются. Для изменения порта тестового сервера:
`npm run mock:server -- --port 3001`.

Дополнительные настройки инструментов:

- `DB_PORT=27017` — порт MongoDB на хосте для Docker Compose (значение по умолчанию
  27017). При изменении укажите тот же порт в URI команды импорта.
- `TEST_MONGODB_URI=mongodb://127.0.0.1:27017` — необязательный адрес сервера
  для интеграционных тестов. По умолчанию используется локальный порт 27017.
  Тесты создают и удаляют только отдельные базы с префиксом `six_cities_test_`.

## Окружение

Для удобства работы над проектом используются инструменты из **Node.js** и **npm**. Все необходимые настройки произведены. Убедитесь, что на рабочем компьютере установлен актуальный LTS релиз Node.js**. Актуальная версия **Node.js** указана в файле `package.json` в поле `node`. Затем, в терминале, перейдите в директорию с проектом и _единожды_ запустите команду:

```bash
npm install
```

Команда запустит процесс установки зависимостей проекта из **npm**.

### Сценарии

В `package.json` предопределено несколько сценариев.

#### Поднять и остановить MongoDB

`npm run db:up` запускает MongoDB через Docker Compose и ожидает её готовности.
`npm run db:down` останавливает контейнеры, сохраняя том с данными.

#### Проверить работу с настоящей MongoDB

```bash
npm run db:up
npm run test:db
```

Собирает проект и выполняет четыре интеграционных теста: создание и поиск пользователей,
хеширование пароля и уникальность email, полный импорт с проверкой ссылок и временных
полей, частичный импорт при ошибке, недоступность сервера без утечки реквизитов.
Проверки выполняются в отдельных временных базах, которые удаляются после тестов.

#### Проверить приложение тестами

```bash
npm test
```

Собирает проект и запускает тесты стандартным модулем `node:test`:
генерация и обратное чтение TSV, диапазоны значений, границы блоков UTF-8,
обработка ошибок и полный цикл CLI через локальный HTTP-сервер.
Дополнительно проверяются загрузка `.env`, приоритет переменных окружения,
обязательность настроек, валидация порта/IP/соли, JSON-логи и pino-pretty,
код завершения при ошибке, отсутствие секретов в логах и внедрение зависимостей.
Тесты создают временные файлы и удаляют их после завершения.

#### Запустить тестовый JSON-сервер

```bash
npm run mock:server
```

Запускает json-server с `mocks/mock-server-data.json` на порту 3000.
Ресурс `http://localhost:3000/offers` возвращает заготовки для `--generate`.
Изменения файла отслеживаются автоматически.

#### Запустить CLI

```bash
npm run cli -- --import ./mocks/test-data.tsv mongodb://127.0.0.1:27017/six_cities
```

Собирает проект и выполняет указанную команду CLI. Без аргументов выводит справку.

#### Скомпилировать проект

```bash
npm run compile
```

Создаст директорию `dist` и скомпилирует проект.

#### Удалить скомпилированный проект

```bash
npm run clean
```

Удаляет директорию `dist`. Используется перед компиляцией.

#### Собрать проект

```bash
npm run build
```

Выполняет сборку проекта: удаляет ранее скомпилированный проект и компилирует заново.

#### Проверить линтером

```bash
npm run lint
```

Запуск проверки проекта статическим анализатором кода **ESLint**.

Линтер проверяет файлы только внутри директории `src`.

**Обратите внимание**, при запуске данной команды, ошибки выводятся в терминал.

#### Запустить ts-модуль без компиляции

```bash
npm run ts -- <Путь к модулю с ts-кодом>
```

Пакет `ts-node` позволяет выполнить TS-код в Node.js без предварительной компиляции. Используется только на этапе разработки.

#### Запустить проект

```bash
npm start
```

Собирает проект и запускает REST-приложение с JSON-логами Pino.

#### Запустить проект с форматированными логами

```bash
npm run start:pretty
```

Собирает проект и запускает REST-приложение с транспортом pino-pretty.
Этот сценарий предназначен для разработки, пакет pino-pretty установлен
как dev-зависимость.

## Структура проекта

### Директория `src`

Исходный код организован по назначению:

- `src/main.cli.ts`, `src/main.rest.ts` — точки входа CLI и REST-приложения.
- `src/cli` — команды CLI и обработка аргументов.
- `src/rest` — класс `Application` и контейнер REST-приложения.
- `src/shared/libs/<module>` — общие инфраструктурные модули: `logger`, `config`, `database`.
- `src/shared/modules/user`, `src/shared/modules/offer` — сущности, схемы,
  интерфейсы и сервисы пользователей и предложений, общие для CLI и REST.
- `src/shared/container.ts` — общие зависимости, `src/cli/cli.container.ts` — контейнер CLI.
- `src/shared/types` — идентификаторы компонентов DI.
- `src/shared/file-reader`, `src/shared/file-writer` и вспомогательные функции —
  существующие средства работы с TSV и генерации данных.
- `src/types` — типы предметной области и заготовок.
- `tests` — проверки CLI и инфраструктуры.

Названия файлов записываются в kebab-case. Интерфейсы получают суффикс
`.interface.ts`, типы — `.type.ts`, схемы — `.schema.ts`, контейнеры — `.container.ts`.
Для нового общего модуля создавайте отдельную папку в `shared/libs`, храните
его контракт и реализацию рядом. Общие предметные модули размещайте
в `src/shared/modules/<module>`, а будущие HTTP-контроллеры — в REST-части.

Все зависимости компонентов REST-приложения и импорта передаются через конструкторы.
Классы `Application`, `PinoLogger` и `RestConfigService` помечены `@injectable()`.
`@inject(Component.Logger)` и `@inject(Component.Config)` связывают параметры
с интерфейсами; контейнер сопоставляет идентификаторы с реализациями.
Настройки самого логера также регистрируются в контейнере.
Компоненты имеют область singleton: один экземпляр на контейнер.
`reflect-metadata` загружается до классов с декораторами.
Разрешение зависимостей через `container.get` выполняется в точке входа,
внутри компонентов новые зависимости вручную не создаются.

Общий контейнер регистрирует соединение Mongoose, клиент БД, модели `User`/`Offer`
и сервисы `UserService`/`OfferService`. `UserService` предоставляет `create`,
`findById`, `findByEmail`; `OfferService` — `create` и `findById`.
Каждый контейнер использует собственное соединение и собственные модели.
Схемы создают отдельные коллекции `users` и `offers`; `authorId` — ObjectId со ссылкой на `User`.
